* Introduction
This program is an image acquisition software mainly intended for cameras, by using the [[https://github.com/genicam/harvesters][Harvester]] package in combination with [[https://www.pyqtgraph.org/][PyQtGraph]] (that's where the pg in the name comes from). Furthermore it is possible to use more generic cameras via OpenCV.

* Installation
Do yourself a favour and install [[https://github.com/astral-sh/uv][uv]]. Running this program is then as easy as going into the directory and executing:
#+begin_src
uv run ui.py
#+end_src

* Configuration
Available cameras should be automatically detected on startup. GenTL Producers (*.cti files) will be detected in every path listed in the environment variable ~GENICAM_GENTL64_PATH~ (colon-separated, analogous to [[https://github.com/AravisProject/aravis][aravis]]). As a fallback, the well-known Allied Vision install locations (Vimba X under ~\/opt\/alliedvision~, classic Vimba under ~\/opt/Vimba*~) are scanned as well. If no GenTL Producer could be found, you can manually select the file via the menu bar settings. When several producers are installed, connecting picks the one that actually enumerates the selected camera.

Because feature node names differ between camera families (SFNC ~ExposureTime~ vs. classic Allied Vision ~ExposureTimeAbs~, etc.), the UI resolves them through small per-camera profiles in [[file:camera_profiles.py][camera_profiles.py]]. The matching profile is auto-detected from the node map on connect; to support a new camera family, add one ~CameraProfile~ entry there. Cameras exposing ~ExposureAuto~ / ~GainAuto~ get an ~Auto~ checkbox on the right of the exposure/gain rows. The FPS spinbox cap follows the connected camera's reported maximum frame rate.

The image size applied in the settings panel is stored per camera (vendor/model/serial) in =~/.config/harvesters_pg/camera_resolution.json= and re-applied when that camera connects again.

* Region of interest (camera AOI)
The camera can read out only part of its sensor, which raises the frame rate and shrinks recordings. Besides typing a size and pressing /Apply/, you can draw the region on the live view: press /Select ROI/ next to the image size (available while a GenICam camera is live, not for webcams, during a recording or while a loaded file is shown), then left-drag a box over the image. The label at the box shows its size and the camera AOI it becomes; Esc cancels. While the tool is active the view does not pan or zoom.

On release the box is applied right away: it is clamped to the current frame, shifted by the current ~OffsetX~ / ~OffsetY~ (so a box drawn on an already cropped image lands on the right sensor pixels) and snapped to the camera's ~Width~ / ~Height~ / offset increments, rounding inwards; a box smaller than the camera's minimum size is enlarged to it. Cameras without offset nodes keep the AOI at the sensor origin and extend it to the box's far edge. The view fits the new AOI once, and the AOI is saved per camera like the image size. /Full sensor/ restores the whole sensor at offset 0 (~WidthMax~ x ~HeightMax~; cameras without those use ~SensorWidth~ / ~SensorHeight~, or ~Width~ / ~Height~ maximum with the offsets at 0).

Every AOI change (/Apply/, /Select ROI/, /Full sensor/) re-opens the camera the way Disconnect + Connect does: the live view stops, the camera's acquisition is closed (data stream and buffers released), the camera is opened again, the AOI is written before it starts, and the live view resumes if it was running. On the CoaXPress rig (Active Silicon grabber) a new image size only took effect that way; changing it between a stop and a start of the same acquisition gave a black view and was followed by fatal PCIe errors. Exposure, gain, frame rate and the other camera settings stay as they are. The AOI controls are disabled while a change runs and for a second afterwards; if no frame of the new size arrives within 2 s, the status bar says so. Connecting a camera without a saved AOI resets it to the whole sensor, offsets included.

To check what a camera and its frame grabber report around an AOI change, close harvesters_pg and run ~uv run aoi_probe.py~: it opens the first camera, streams a few frames, shrinks the AOI a little (the same safe re-open), streams again, restores the AOI and prints the camera, grabber and data stream values at every step. It changes the camera's AOI while it runs.

* Recording
It is possible to record video. The frames can be inspected in the main window and saved as image sequence or in a h5 file.

h5 files carry the recording's metadata as root attributes: the camera settings, ~fps~, ~timestamp~ (local start time of the recording, ~%Y%m%d%H%M%S~) and ~recording_id~, a random UUID. The camera settings are read right after the recording, so a recording can still be saved after disconnecting the camera. Every file saved from one recording, also after loading it again, carries the same ~recording_id~. The tracking scripts copy these attributes into the trajectory files, so results can be matched to their recording. The datasets ~timestamps~ and ~frame_counters~ are only written for cameras that superimpose the Mikrotron info fields on Mono8 frames.

A recording that would not fit into the available RAM is refused before it starts (filling the RAM would make the whole machine swap). If the camera stops delivering in the middle of a recording, the frames recorded until then are kept. While a recording runs, the window cannot be closed and the camera controls are locked.

The optional fields /Particles/ and /Objective/ next to the frame count take the lab ids of the particle batches (comma-separated) and of the objective, as used for their entries in NOMAD. They are saved with each recording as attributes ~particles~ and ~objective~; NOMAD links the video and its tracks to these entries. Loading a recording shows its own values in the fields.

* Replay
It is possible to load a h5 file and show the video, click on File and open to do so.

* Troubleshooting
The program logs to ~harvesters_pg.log~ in the working directory (~--log-file~ to change it, ~-v~ / ~-vv~ for more detail). If it crashes inside a GenTL producer, the stack traces of all threads are written to the same file, so attach it when reporting a crash or freeze.
